# 活动交互方案梳理技能

## 活动系统现有架构

活动系统由多个服务组成，梳理交互方案时需要了解各服务的职责和通信方式。

### 后端服务

| 服务 | 仓库 | 职责 |
|------|------|------|
| **活动中控服务 (xlogic)** | hdpt_activity_xlogic | 活动核心逻辑：事件消费、状态管理、与前端交互、频道广播、用户单播 |
| **抽发奖服务** | hdpt_award | 奖包配置管理、抽发奖逻辑执行，中控服务通过奖池id/奖包id调用 |
| **挂件服务** | hdpt_materials | 控制挂件的显示/隐藏、挂件列表查询、挂件变化广播。只管显隐，不管玩法数据 |
| **排行榜服务** | hdpt_ranking | 排行榜数据管理 |

### 通信方式

活动系统与前端有四种通信方式，交互方案中需要明确每个交互走哪种：

| 方式 | 方向 | 触发方 | 目标 | 典型场景 |
|------|------|--------|------|----------|
| **Kafka 消费** | 外部→活动 | 外部业务服务 | 活动中控服务 | 业务生命周期事件（PK开始/结束、送礼等） |
| **HTTP 请求** | 前端→活动 | 前端主动 | 活动中控服务 | 页面数据拉取、用户主动操作（抽奖、报名等） |
| **频道广播** | 活动→前端 | 活动中控/挂件服务 | 房间全量用户 | 挂件显隐、玩法数据更新、特效触发 |
| **用户单播** | 活动→前端 | 活动中控服务 | 指定用户 | 弹窗提示（活动介绍、获奖通知、状态变更） |

### 服务职责边界

以下是容易混淆的职责划分：

- **挂件服务** 只控制挂件的显示/隐藏（通过挂件广播），不负责下发玩法数据
- **玩法数据变更** 由中控服务直接频道广播到前端，不经过挂件服务中转
- **活动中控服务** 是唯一的事件消费方和逻辑处理方，其他服务被中控调用
- **抽发奖服务** 不直接与前端交互，由中控服务代为调用

### 前端入口类型

活动前端通常有以下几种入口，按需组合：

| 入口 | 载体 | 数据来源 | 说明 |
|------|------|----------|------|
| 玩法Web页 | 独立H5 | HTTP查询后端 | 宣发用，展示规则、奖励 |
| 频道内挂件 | 房间模板 | 挂件广播(显隐) + 频道广播(数据) | 活动期间房间内显示，实时数据 |
| 频道内弹窗 | PC内嵌页H5 / App H5弹窗 | 单播触发 + HTTP查询 | 详细信息展示、交互操作 |
| 玩法页H5 | H5 | HTTP查询后端 | 玩法数据、榜单、任务等 |

### 活动与外部业务的对接模式

活动作为**旁路服务**，通过消费外部业务的 Kafka 事件来驱动活动逻辑，不侵入业务核心代码。

```
外部业务服务 --Kafka事件--> 活动中控服务 --广播/单播--> 前端
                                    |
                                    +--> 挂件服务(显隐)
                                    +--> 抽发奖服务(发奖)
```

如果外部业务没有现成的事件，需要标记 TODO 让业务方新增，而不是在活动侧自行计算（如不消费原始送礼流水自行算分，而是让PK服务发出权威的分数变化事件）。

## 目标

从需求文档出发，梳理活动与各业务服务之间的前后端交互方案。产出一份面向前后端开发的交互文档，
让开发者清楚：有哪些入口、走什么通信方式、消费哪些事件、前端如何响应、异常怎么处理。

交互方案**重功能、轻字段**——关注事件的含义和触发时机，不深入 proto 字段定义（那是技术方案阶段的事）。

## 工作流程

### 第一步：理解需求

读取用户提供的需求文档（PRD），提取以下关键信息：

1. **活动玩法**：核心玩法是什么，有哪些阶段
2. **用户入口**：用户从哪里看到/参与活动（Web页、挂件、弹窗、H5等）
3. **依赖业务**：活动依赖哪些外部业务服务（PK、匹配、房间、送礼等）
4. **奖励机制**：有没有抽奖、发奖、排行榜等

### 第二步：调研已有能力

这一步是交互方案质量的关键——搞清楚哪些事件/接口已经存在，哪些需要新增。

#### 搜代码仓库

在本地代码仓库（`D:/java-project/`）中搜索相关的：
- Kafka topic 和 listener（确认事件是否存在）
- 广播定义（proto 中的 bro/broadcast）
- 服务间调用（RPC/HTTP provider）

**如果本地没有对应仓库，用 `sg` 命令搜索远程代码。**

#### 辨别容易混淆的概念

很多业务有相似但不同的概念（如跨厅PK vs 跨业务PK），必须通过代码确认，不能想当然。
搜到事件后，读一下 listener 的注释和处理逻辑，确认确实是你需要的那个。

### 第三步：输出交互方案文档

文档结构如下：

```markdown
# {活动名称} 前后端交互文档

## 一、总体交互架构

### 1.1 用户侧入口
mermaid flowchart + 入口说明表

### 1.2 后端服务架构
mermaid flowchart（含外部业务服务、Kafka、活动后端、前端四层）

### 1.3 事件定义（活动中控消费）
Kafka topic 表（含含义、触发时机、活动用途、状态）

### 1.4 通信方式
通信方式汇总表（Kafka/HTTP/频道广播/用户单播）

## 二、核心流程图
mermaid 时序图，按阶段拆分完整生命周期

## 三、前端状态机
mermaid stateDiagram，展示前端视角的状态流转

## 四、前端关键交互说明
按组件分组（挂件、弹窗、特效等），说明事件来源和前端行为

## 五、异常与边界处理
异常场景 + 处理策略表
```

### 各部分的写作要点

#### 服务架构图

明确区分各服务的职责边界：
- **活动中控服务**：事件消费、活动逻辑、与前端交互、广播和单播
- **挂件服务**：只控制挂件的显示/隐藏，不负责下发玩法数据
- **抽发奖服务**：奖包配置、抽奖逻辑
- 玩法数据变更由中控服务直接频道广播到前端

#### 事件定义

用表格列出所有事件，每个事件说明：
- 含义：这个事件代表什么
- 触发时机：什么时候发出
- 活动用途：活动拿到这个事件后做什么
- 状态：已有 / **TODO: 待新增**

已有事件写明 topic 名称；缺失的事件标记 TODO，说明需要在哪个服务新增。

活动作为旁路服务，优先消费已有事件，不侵入业务核心代码。
实在没有的事件，标记 TODO 并说明需要业务方配合新增。

#### 流程时序图

- 按阶段拆分（如：匹配成功 → PK进行中 → 触发活动 → 活动进行中 → PK结束 → 发奖）
- 区分不同通信方式：Kafka 用实线箭头、单播用虚线箭头
- 标注关键判断条件

#### 前端交互说明

按组件分组，每个交互说明事件来源（挂件服务 / 中控服务 / HTTP 响应）：
- 挂件：谁控制显隐，谁下发数据
- 弹窗：单播类型、目标用户、前端行为
- 特效/动画：触发条件、持续时间、用户操作

#### 异常与边界处理

列出所有能想到的异常场景：
- 上限/次数控制
- 用户退出重进
- 奖池耗尽
- 新进房用户
- 并发/时序问题

### 第四步：与用户对齐

输出初稿后，重点和用户确认：
1. 事件是否找对了（最容易出错的地方）
2. 通信方式是否合理（广播 vs 单播 vs HTTP）
3. 各服务的职责边界是否正确
4. 有没有遗漏的异常场景

根据反馈迭代修改文档。

### 第五步：沉淀知识

任务完成后，回顾是否有新知识需要沉淀到知识图谱：
- 新发现的事件/topic
- 业务概念的区别（如跨厅PK vs 跨业务PK）
- 服务间的依赖关系

## 常见陷阱

### 事件找错
同一业务可能有多套事件体系（如跨厅PK走邀请制，跨业务PK走匹配制），
topic 前缀和处理类完全不同。必须通过代码确认 listener 的注释和处理逻辑。

### 混淆服务职责
挂件服务只管显示/隐藏，不是所有挂件相关的数据都经过它。
玩法数据变更由中控服务直接广播，不走挂件服务中转。

### 过度设计
交互方案阶段不需要定义具体的 proto 字段、数据库表结构。
只关注"有什么事件、干什么用、谁发给谁"这个层面。

### 遗漏上报
前端弹窗类交互，如果需要防止重复触发（退出重进），
要设计上报机制——用户看到弹窗时即上报，而不是等用户操作后才上报。

### 不必要的请求
纯前端行为（如开始播放动画）不需要发请求到后端，
只有需要后端记录或返回数据的操作才需要 HTTP 请求。
